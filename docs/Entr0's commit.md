# Entr0's Commit — RAVEN Foundation

## Why this architecture exists

This commit establishes the first working foundation for RAVEN rather than trying to build the entire research platform at once.

The goal of this stage was simple: prove that the core execution path works from beginning to end before adding autonomous agents, mutation logic, external model adapters, dashboards, or larger research suites.

RAVEN is intended to become a repeatable LLM security-evaluation framework. For that to work, the evidence generated by the framework needs to be understandable, reproducible, and attributable to a specific configuration and source state.

That meant the first priority was not complexity. It was establishing a trustworthy pipeline.

## Current execution path

The working v0.1 path is:

```text
Configuration
      ↓
Authorization / Safety Validation
      ↓
Baseline Suite Loader
      ↓
Orchestrator
      ↓
Mock Target Adapter
      ↓
Response Capture
      ↓
Deterministic Rule Evaluator
      ↓
Structured JSONL Archive
      ↓
Console Report
```

Each stage is intentionally separated so that future implementations can be replaced or expanded without requiring the rest of the framework to be rewritten.

The mock target is especially important at this stage. It allows RAVEN's orchestration, evaluation, storage, reporting, and safety behavior to be tested without depending on an external API or live model.

## Authorization first

Authorization is treated as part of execution state rather than an assumption made by the operator.

The initial configuration requires an explicit authorization confirmation and defined scope reference.

The current implementation also restricts execution to the local mock adapter.

This is intentional.

Network-backed adapters should only become available when they can inherit the same authorization, allowlisting, request-budget, timeout, and scope controls used by the core framework.

RAVEN should fail closed when authorization requirements are not satisfied.

## Why the baseline comes before mutation

Mutation will eventually become one of the more interesting parts of RAVEN, but it is intentionally not active yet.

Before RAVEN can intelligently create new adversarial inputs, it needs a stable reference point.

The initial baseline suite provides that reference.

The first baseline currently tests controlled disclosure behavior, instruction-boundary handling, and malformed-input handling using completely synthetic data.

These cases are not intended to represent the final research dataset. Their purpose is to prove that a testcase can move through the complete system and produce structured evidence.

Mutation will be added only after this baseline behavior remains predictable.

## Evidence and reproducibility

Every execution receives a unique RAVEN run identifier.

A run currently records:

- run ID
- suite
- target
- model identifier
- random seed
- RAVEN Git commit
- Git working-tree state
- configuration hash
- execution timestamp
- executed testcases
- captured responses
- evaluation results

Testcases, responses, and evaluations are stored separately as JSONL records.

Executed testcases are treated as evidence rather than temporary application state. Future mutations should therefore create new child cases instead of rewriting their parents.

This allows mutation lineage and historical behavior to remain inspectable.

Run artifacts are intentionally excluded from Git by default because future security-testing output could contain sensitive material.

## Evaluation model

The first evaluator is deliberately deterministic.

It compares captured responses against expected properties such as required and forbidden substrings.

This is enough to test the execution pipeline without introducing another model whose behavior could complicate or obscure early results.

Future RAVEN versions can add additional referee strategies such as semantic evaluation, classifiers, model-assisted judging, or human review.

Those strategies should remain replaceable implementations behind a common evaluation boundary.

## Current validation

The initial foundation has successfully demonstrated the following:

- Python development environment builds correctly
- RAVEN installs as an editable package
- configuration validation works
- authorization gates reject invalid configuration
- the mock target behaves deterministically
- the orchestrator executes the full baseline
- evaluation logic identifies expected and forbidden behavior
- JSONL evidence is archived successfully
- archived results can be reported without rerunning the target
- automated tests pass
- Ruff validation passes

The first complete development baseline executed three synthetic testcases and returned three PASS results.

That proves the minimum RAVEN execution loop is operational.

## What is intentionally incomplete

Several directories and interfaces exist before their full implementations.

This is intentional architectural scaffolding rather than unfinished behavior being presented as complete.

The following remain future work:

- Generator Agent
- Referee Agent abstraction
- Mutation Agent
- advanced Archivist behavior
- mutation strategies
- mutation lineage
- SQLite storage
- external model adapters
- OpenAI-compatible targets
- local-model adapters
- regression comparison
- HTML reporting
- CI/CD integration
- MCP integration
- dashboard and visualization
- larger adversarial research suites

The framework should not gain these components simply because they are interesting.

Each should be introduced when the layer beneath it is stable enough to support it.

## Next steps

### Phase 1 — Harden the foundation

The next development pass should improve the current core before adding autonomous behavior.

Priorities:

1. Expand configuration validation tests.
2. Add explicit tests for request budgets and target allowlisting.
3. Record additional reproducibility metadata where useful.
4. Improve error handling around malformed suites and archived runs.
5. Add type-checking validation with mypy.
6. Validate the Docker development path.
7. Document contributor setup and development commands.

### Phase 2 — Target abstraction

Once the local pipeline is stable:

1. Finalize the target adapter contract.
2. Add stronger adapter-level tests.
3. Implement a local model target.
4. Design the authorized OpenAI-compatible adapter.
5. Apply explicit allowlisting and network safety controls before external requests are enabled.

The core orchestrator should not need to know which model provider is behind an adapter.

### Phase 3 — Agent system

After target execution is stable:

1. Introduce the Generator abstraction.
2. Move evaluation behind the Referee abstraction.
3. Implement controlled mutation strategies.
4. Add parent/child mutation lineage.
5. Expand Archivist responsibilities where required.

Agent behavior should remain observable and bounded.

### Phase 4 — Regression engine

RAVEN's larger value comes from comparing security behavior over time.

The framework should eventually answer more than:

> Did this testcase pass or fail?

It should also answer:

> What changed compared with the previous known baseline?

This phase should introduce run comparison, newly failing cases, newly mitigated cases, category summaries, and machine-readable regression reports.

## Architectural principle going forward

RAVEN should prioritize evidence over spectacle.

A complicated autonomous system is not useful if nobody can explain what it executed, why it reached a conclusion, or whether the result can be reproduced.

Every major feature should continue answering the same questions:

- What was tested?
- Why was it tested?
- What configuration was used?
- What code produced the run?
- What response was observed?
- How was that response evaluated?
- Can another researcher reproduce it?
- What changed relative to previous runs?

If RAVEN can continue answering those questions as the platform becomes more capable, then the architecture is doing its job.
